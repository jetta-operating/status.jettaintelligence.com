# Status Site Operating Model

## North star

This repo should operate a private status plane for Jetta-managed services and
critical vendor dependencies.

The site should be:

- simple enough for leadership to understand in 30 seconds,
- detailed enough for operators to know where to look next,
- protected enough that internal service posture is not casually public,
- boring enough that it remains trustworthy during an incident.

Upptime remains the status renderer and external check runner. Cloudflare
Access should own access control. Deeper app-specific probes should live in the
systems they test and report up.

## Surface model

| Surface | Audience | Content |
|---|---|---|
| Public status | customers, external partners | public-facing services, friendly names, no internal topology |
| Private status | Jetta/AIC/Greenmark operators and leadership | internal tools, vendor dependencies, incident detail, response-time history |

`status.jettaintelligence.com` is currently treated as the private operating
surface. Until Cloudflare Access or equivalent edge authentication is in place,
avoid adding sensitive service names, private endpoints, tokens, or incident
details.

## Responsibilities by layer

| Layer | Owns | Should not own |
|---|---|---|
| Upptime | 15-minute external availability checks, static status rendering, GitHub issue incidents | identity, secrets, private auth, deep product correctness |
| Cloudflare Access | who can see the site before content loads | uptime checks, incident history, monitor definitions |
| Service repos | real product smoke tests, authenticated checks, domain runbooks | global status page governance |
| Docs in this repo | naming, taxonomy, access-control rules, monitor lifecycle | live state that should be generated by Upptime |

## Service taxonomy

Use this taxonomy when adding monitors or discussing status:

1. Jetta websites and identity surfaces
2. AIC and Jetta-managed application surfaces
3. Greenmark and Cerebro surfaces
4. Infrastructure vendors and control planes
5. AI vendor surfaces and public component-status APIs
6. Deprecated or paused checks

The source config (`.upptimerc.yml`) is ordered using this taxonomy. See
[`service-catalog.md`](./service-catalog.md) for the current monitor list.

## Status meanings

Use these meanings when interpreting the page and writing incidents:

| Status | Meaning |
|---|---|
| Operational | Endpoint responds with an expected status code and is not known degraded. |
| Degraded | Endpoint responds, but behavior, latency, upstream vendor state, or a related product check indicates partial impairment. |
| Down | Endpoint fails the expected contract or is unavailable. |
| Paused / deprecated | Intentionally not monitored as an active obligation. |

Do not equate "green" with "the whole business process works." Upptime checks
are external probes. Some business-critical facts need deeper app or data
quality checks elsewhere.

## Monitor rules

Add a monitor only when all of these are true:

- The endpoint represents a current operational obligation.
- The URL is public or intentionally safe to expose in this repo.
- The expected status codes are explicit when the endpoint normally returns
  something other than `200`.
- The service name is safe for the intended audience.
- The owner/runbook path is known or captured in docs.

Do not add:

- bearer tokens,
- invite links,
- private API keys,
- internal-only hostnames that should not be public,
- one-off experiments,
- retired service URLs,
- checks that require browser login unless the probe is designed elsewhere.

## Incident workflow

Every real incident should answer:

1. What failed?
2. Who owns it?
3. Is this our system, a vendor, or unknown?
4. What user/business impact exists?
5. What changed or what was investigated?
6. When was it resolved?
7. What follow-up, if any, prevents recurrence?

Upptime issues are the event log. Human incident notes should preserve
judgment, impact, and next action.

## Access-control rule

If the site contains only public-friendly service names and status history, it
can remain public.

If the site contains internal service posture, vendor dependency posture, or
private incident context, it should be protected before content loads. The
recommended path is Cloudflare Access with one-time PIN or company identity
provider login.

See [`access-control.md`](./access-control.md) and [`faq.md`](./faq.md).

## Vendor component-status limits

Vendor component feeds are useful but not complete.

For Claude/OpenAI/Codex, this repo can monitor:

- vendor status pages,
- vendor component-status JSON APIs,
- public web/login surfaces,
- unauthenticated API model endpoints where `401` is the expected healthy
  response.

This does not prove a specific paid model can complete an authenticated request
from our account. Model-level checks should be authenticated probes owned by
the relevant application or ops repo, then summarized here if needed.

## Definition of done for future evolution

The status plane is "good enough" when:

- access control matches the sensitivity of the content,
- monitor names are grouped and safe,
- every active monitor has a current owner or runbook path,
- deprecated checks are documented instead of silently removed,
- incident issues answer impact and ownership,
- external vendor checks distinguish page uptime from component health,
- deeper app/data probes live outside Upptime and report up cleanly.
