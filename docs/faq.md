# Status Site FAQ

## What problem are we solving?

We want a lightweight private status page for Jetta/AIC/Greenmark-managed
systems without exposing internal service posture publicly.

The site should answer: "Are the things we depend on working?" It should not
accidentally publish sensitive implementation details, outage patterns, or
vendor dependency posture to the open internet.

## Why not just leave it public?

Public status pages are useful when the intended audience is customers or the
general public.

This page is different. It monitors a mix of company websites, operational
tools, vendor dependencies, and internal-facing surfaces. Some service names,
outages, vendor dependencies, or incident histories may reveal internal
architecture or operating risk. If the audience is limited to Jetta/AIC/
Greenmark leadership and operators, the page should be access-controlled.

## Is this real security or just a password screen?

Cloudflare Access is real edge authentication.

A static password screen is not enough for sensitive status content because the
HTML, JavaScript, status JSON, and history files can still be served to the
browser. A technical user can inspect the shipped files or network requests and
bypass a client-side prompt.

Real security means the request is authenticated before the site content is
served.

## How easy is login?

The preferred flow is one-time PIN.

1. User opens `https://status.jettaintelligence.com`.
2. Cloudflare Access asks for the user's email.
3. Cloudflare sends a one-time PIN.
4. User enters the PIN.
5. The status page loads.

This keeps the experience simple without creating a shared password that can
leak or be reused.

## What does it cost today?

Expected cost is `$0/month` if the approved audience stays under Cloudflare's
free Zero Trust user limit.

Cloudflare publicly describes the Zero Trust free tier as intended for teams
under 50 users. That should cover the likely access list for this status page.

## What happens if we grow past the free tier?

Budget roughly `$7/user/month` for paid Cloudflare Zero Trust seats based on
Cloudflare's public pay-as-you-go pricing.

This should be revisited before adding broad company-wide access. For a small
operator/leadership audience, the expected cost remains zero.

## Does this create vendor lock-in?

Low lock-in.

The status site is still static files generated by Upptime and GitHub Actions.
Cloudflare Access is the gate in front of the site, not the status data model
or monitoring engine.

If needed later, the generated static site can move to another authenticated
host or reverse proxy.

## Can someone bypass it?

It depends on the hosting/source setup.

If only the custom domain is protected but the GitHub repository, raw GitHub
history files, or GitHub Pages origin remain public, a technical user may still
discover the underlying status data.

For stronger protection, use a private repo and/or serve generated status
assets through a private authenticated path. See
[`access-control.md`](./access-control.md).

## What is the implementation risk?

Low, but not zero.

Main risks:

- DNS/proxy mistakes while moving the hostname behind Cloudflare Access.
- Accidentally leaving raw status data public.
- Locking out approved users.
- Confusing users with too many login options.
- Breaking deep links such as `/history/<slug>/`.

All of these are testable. The rollout should include an incognito-browser test
for approved and unapproved users, plus checks that static assets and history
routes are protected.

## What is the recommended path?

Recommended path:

1. Keep Upptime as the monitor/status generator.
2. Put `status.jettaintelligence.com` behind Cloudflare Access.
3. Use one-time PIN or the chosen company identity provider.
4. Limit access to approved people/groups.
5. If the content becomes meaningfully sensitive, move the repo/source or raw
   status data behind a private path too.

This gives an easy user experience now and leaves a clear path to stronger
privacy later.

## Can Codex set up Cloudflare itself?

Yes, if Codex has a Cloudflare API token with the right scopes.

This repo now has an idempotent setup script:

```bash
CLOUDFLARE_API_TOKEN=... tools/configure_cloudflare_access.py --apply
```

The script configures the lowest-friction security shape:

- DNS record for `status.jettaintelligence.com` proxied through Cloudflare,
- Cloudflare Access self-hosted application for the status hostname,
- reusable allow policy for approved email domains,
- one-week session duration for a low-friction operator experience.

The script does not print the token. It refuses to mutate anything unless
`--apply` is passed.

## What should the initial Cloudflare Access policy allow?

Start small.

The repo automation defaults to these email domains:

- `jettaintelligence.com`
- `aicholdings.com`
- `greenmarkwaste.com`

For tighter control, run the script with explicit domains or edit the policy in
Cloudflare to use named email addresses instead. A named-email policy is
stricter; a domain policy is easier to operate.

## How do we know Cloudflare Access is actually protecting it?

Run:

```bash
tools/configure_cloudflare_access.py --verify-only
curl -sSI https://status.jettaintelligence.com/ | sed -n '1,20p'
```

Good signal: the public request is redirected or blocked by Cloudflare Access
before the page content loads.

Bad signal: the public request returns `HTTP/2 200` with `server: GitHub.com`.
That means the status page is still public at the custom hostname.
